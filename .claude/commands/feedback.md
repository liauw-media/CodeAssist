# Feedback

Submit feedback, bug reports, or feature requests — auto-creates GitHub issues with full context.

## Input
$ARGUMENTS

## Execute

### Step 1: Collect context automatically

Gather environment info (do NOT ask the user for this):

```bash
# Version
VERSION=$(cat .claude/VERSION 2>/dev/null || echo "unknown")

# OS
OS=$(uname -s 2>/dev/null || echo "unknown")

# Current branch
BRANCH=$(git branch --show-current 2>/dev/null || echo "unknown")

# Last 3 commits (for context)
RECENT_COMMITS=$(git log --oneline -3 2>/dev/null || echo "none")

# Check gh CLI availability
gh --version > /dev/null 2>&1 && GH_AVAILABLE=true || GH_AVAILABLE=false
```

### Step 2: Detect feedback source

Analyze $ARGUMENTS to determine:

**If $ARGUMENTS is empty or unclear**, ask the user: "What would you like to report? Describe what happened or what you'd like to see improved."

**Type** (pick one):
- `bug` — Something broken or not working as expected
- `feature` — New functionality wanted
- `improvement` — Existing feature could be better
- `docs` — Documentation issue or improvement

**Related component** (auto-detect from context):
- If the user mentions a command (e.g., `/design`, `/review`), tag it
- If the user mentions a skill, tag it
- If from within a command execution that failed, tag that command
- If none detected, use `general`

### Step 3: Build the issue

**Labels** (comma-separated for gh CLI):
- Always include the type label: `bug`, `feature`, `improvement`, `docs`
- Add component label if detected: `command:design`, `skill:tdd`, `agent:architect`, etc.
- Add `user-feedback` label to all issues

**Title format:** `[type] brief description`

**Body template:**

```markdown
## Context

| Field | Value |
|-------|-------|
| **Version** | {VERSION} |
| **OS** | {OS} |
| **Branch** | {BRANCH} |
| **Component** | {detected command/skill/agent or "general"} |

## Description

{User's feedback, expanded into a clear description}

## Expected Behavior

{What should happen — infer from context if bug report}

## Current Behavior

{What actually happens — from user's description}

## Steps to Reproduce

{If bug: numbered steps. If feature/improvement: "N/A"}

## Recent Commits

```
{RECENT_COMMITS}
```

## Additional Context

{Any relevant details from the conversation}

---
*Auto-generated by `/feedback` — [CodeAssist](https://github.com/liauw-media/CodeAssist)*
```

### Step 4: Preview and submit

Show the user a preview:

```
## Feedback Preview

**Type:** {type}
**Component:** {component}
**Labels:** {labels}

**Title:** [type] brief description

**Body:**
{formatted body}
```

**Ask the user to confirm** before submitting: "Ready to create this issue? (yes/no)"

If confirmed and `gh` is available:
```bash
# Try with labels first, fall back to no labels if they don't exist
gh issue create \
  --repo liauw-media/CodeAssist \
  --title "[type]: brief description" \
  --body "formatted body" \
  --label "user-feedback,{type}" 2>/dev/null \
|| gh issue create \
  --repo liauw-media/CodeAssist \
  --title "[type]: brief description" \
  --body "formatted body"
```

After creation, show the issue URL.

**If gh is NOT available:**
Show the manual link:
```
Create manually: https://github.com/liauw-media/CodeAssist/issues/new

Title: [type]: brief description

Body: (copied above)
```

### Step 5: Confirm

```
Issue created: https://github.com/liauw-media/CodeAssist/issues/NNN

Thank you for helping improve CodeAssist!
```

## Self-Report Mode

Commands and skills can trigger feedback by including this in their error handling:

```
If this command fails or produces unexpected results, suggest:
"Something went wrong. Run `/feedback [description of what happened]` to report this."
```

This ensures users always have a path to report issues they encounter during normal usage.

Process the feedback now.
